# Електронний пакет: система управління заявками технічної підтримки

Версія електронного пакета: **1.0.0**. Дата комплектування: **08.11.2026**. Версія прототипу: **0.1.0**.

Навчальний модульний моноліт Python/FastAPI з PostgreSQL. Поточна реалізація — базовий цикл заявки; повний контракт у `api/openapi.yaml` містить також запроєктовані операції.

## Запуск прототипу

Перевірено на Linux x86_64 з Docker Engine і Docker Compose. Потрібні також Python 3 та OpenSSL для початкової локальної конфігурації. Команди виконуються з кореня проєкту.

```bash
python3 prototype/scripts/init_local.py
docker compose --project-directory prototype config --quiet
docker compose --project-directory prototype up -d --build --wait
```

Застосунок: **https://localhost:8443**. Порт доступний лише через loopback; PostgreSQL не публікує порт на хості. Використовуйте саме `localhost`, оскільки дозволене Origin задано як `https://localhost:8443`.

Скрипт генерує окремий `COMPOSE_PROJECT_NAME` для кожної нової локальної конфігурації та випадкові паролі у `prototype/.env`, локальний Root CA та серверний сертифікат у `prototype/.local/`. Повторний виклик зберігає наявні файли. Значення секретів не виводяться; `.env`, ключі й робочі журнали виключені з Git та Docker build context. CA private key не монтується в застосунок.

До відкриття сторінки перевірте локальний CA:

```bash
openssl x509 -in prototype/.local/tls/ca.crt -noout -subject -issuer -dates -fingerprint -sha256
```

Імпортуйте **`prototype/.local/tls/ca.crt`** до довірених CA браузера або сховища ОС, яке використовує браузер. Це свідомо додає довіру до навчального CA на вашому пристрої. Не імпортуйте серверний сертифікат як Root CA і не обходьте перевірку TLS. Скрипти проєкту самостійно системну довіру не змінюють. Автоматичні HTTP-тести використовують цей CA явно, без зміни trust store.

## Навчальні облікові записи

Паролі доступні локально в `prototype/.env`; їх не переносити до записки, скриншотів чи репозиторію.

| Логін | Ролі | Змінна пароля |
| --- | --- | --- |
| requester | Заявник | DEMO_REQUESTER_PASSWORD |
| specialist | Заявник, спеціаліст | DEMO_SPECIALIST_PASSWORD |
| coordinator | Заявник, координатор, спеціаліст | DEMO_COORDINATOR_PASSWORD |
| administrator | Лише адміністратор; доступу до заявок немає | DEMO_ADMIN_PASSWORD |
| other | Інший заявник | DEMO_OTHER_PASSWORD |

Ініціалізація створює одну чергу, одну категорію та політику звичайного пріоритету. Паролі наявних користувачів не скидаються, заявки не видаляються. Зміна `.env` після першої ініціалізації сама по собі не змінює паролі в наявній БД.

## Програмні перевірки

Для тестів на хості потрібні Python 3.12 та `uv`; запуск самого застосунку здійснюється контейнерами. Залежності зафіксовано в `prototype/uv.lock`, для Docker — у `prototype/requirements.lock.txt` з хешами; базові образи зафіксовано digest.

```bash
uv sync --project prototype --frozen
uv run --project prototype pytest -q prototype/tests/test_unit.py
RUN_INTEGRATION=1 uv run --project prototype pytest -q prototype/tests --tb=short
```

**Інтеграційний набір призначений лише для цього навчального середовища.** Він додає синтетичні заявки, тимчасово деактивує користувача `other`, встановлює тестовий тригер відмови історії з подальшим видаленням і перезапускає лише `app` та `db` цього Compose-проєкту. Дані перевірки залишаються у volume; чинні налаштування користувача відновлюються через `finally`. Не запускати ці тести проти робочої БД.

Докази перевірки від 06.11.2026 — `tests/evidence/2026-11-06/`, відповідність TEST-ID — `tests/results.md`. Кількість pytest-перевірок не дорівнює кількості прийнятих TEST-ID.

Необов’язковий браузерний smoke-сценарій — `prototype/scripts/ui_smoke.py`; для нього потрібні Playwright, Chromium, його системні бібліотеки та довіра до локального CA. На початку завжди перевіряються HTTPS, CA і hostname. Для отриманого протоколу використано тимчасовий Chromium з винятком лише для SPKI конкретного тестового сертифіката (`UI_TEST_PIN_CERT=1`); це не налаштування застосунку чи штатного браузера. Клавіатурна доступність цим сценарієм не оцінюється.

## Дані, діагностика та зупинка

```bash
docker compose --project-directory prototype ps
docker compose --project-directory prototype logs --tail 50 app migrate
docker compose --project-directory prototype down
```

Зупинка зберігає volume БД. При повторному `up` міграції та seed запускаються знову без очищення даних. Версія міграції — `0001`; руйнівний downgrade початкової схеми заблоковано. Приклад локальної резервної копії:

```bash
docker compose --project-directory prototype exec -T db pg_dump -U coursework_owner -d coursework -Fc > prototype/.local/backup.dump
```

Діагностика застосунку містить UTC-час, шаблон маршруту, метод, статус, тривалість та correlation ID; тіла запитів і токени не журналюються. У Docker увімкнено ротацію за обсягом; автоматичне дотримання проєктного строку 7 днів ще не реалізовано. Окремо не підтверджені навантажувальний профіль, повна доступність, Windows/ARM64 та придатність до реальної експлуатації.

## Ізоляція копій Compose

COMPOSE_PROJECT_NAME у prototype/.env відокремлює контейнери, мережу та volume БД різних копій. Наявний .env скрипт не переписує. Для старої копії, яка ще не має цього параметра, нове ім’я слід задати лише тоді, коли потрібна окрема порожня БД; попередній volume зберігається. Зміна паролів у .env не змінює паролі в уже ініціалізованій PostgreSQL. Для одночасного запуску двох копій також потрібні різні APP_PORT та відповідні APP_ORIGIN.
