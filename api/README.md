# Контракт програмного інтерфейсу

OpenAPI 3.1.1, версія проєктного контракту 0.1.0; префікс /api/v1. Це специфікація, сервер не реалізовано. 33 операції охоплюють US-01–US-10 та локальний сеанс. Таблиця — operations.md; повна структура — openapi.yaml; синтетичні приклади — examples/. Обсяг реалізації визначає docs/requirements.md, а не наявність операції у специфікації.

## Авторизація та представлення

HTTPS та JSON; браузер і API одного походження. Непрозорий cookie support_session задається сервером з Secure, HttpOnly, SameSite=Strict; сервер зберігає тільки digest токена. Для змін потрібні актуальний X-CSRF-Token та перевірка Origin; login має перевірку Origin до входу. Локальні облікові записи — вибраний навчальний механізм; SSO не додається. Політику паролів, TTL сеансу, throttling та CSRF деталізовано у security/session-policy.md (05.11.2026): Argon2id, абсолютний TTL 8 годин, ротація CSRF через API-ME. Це проєктні рішення, не перевірена реалізація. Базові сеанси потрібні для прототипу; повне адміністрування й сповіщення — за запланованими обсягами.

Активність та поточні ролі/черги перевіряються на кожному запиті, включно з повторами. Роль administrator не надає читання business ticket. DTO входу не містять requesterId, queueId, createdAt, state чи встановлюваних сервером цілей. additionalProperties=false відхиляє їх підміну. Вивід User не містить credential_hash; Ticket не містить payload/outbox/digest. Для заявника внутрішні повідомлення й пов’язані події історії виключаються до пагінації. X-Correlation-ID — відповідь для діагностики, а не ключ повтору. На захищені відповіді встановлюється Cache-Control: no-store.

## Версії та повтори

CreateTicketRequest містить title,description,categoryId та необов’язковий previousTicketId. Перед валідацією BR-01 виконується trim тексту; довжина — кодові точки Unicode, не байти UTF-8. Перевірки клієнта не замінюють сервер. Idempotency-Key — власна домовленість проєкту, UUID у контексті користувача; строк зберігання не менший за існування заявки. Перший запит — 201 і Location; ідентичний повтор — 200 з тим самим id і поточним дозволеним Ticket; інший нормалізований вміст — 409 IDEMPOTENCY_CONFLICT. Подальша деактивація категорії не блокує повтор уже прийнятої операції, але актуальна авторизація потрібна. Повтор технічного 503 допустимий з тим самим ключем; невизначений клієнту результат не є підставою створити новий ключ.

Зміни агрегату містять expectedVersion; UPDATE приймається тільки за збігу поточної tickets.version. Відповідь — нове представлення Ticket з новою version. Застаріла версія — 409 VERSION_CONFLICT. Тут використовується поле команди, а не HTTP If-Match; 412 для нього не застосовується. Версія зростає також від повідомлень і зареєстрованих фонових порушень. Для адміністративних PUT діє expectedVersion; user_roles оновлюються разом із users.version. Для незмінних редакцій політики діє expectedRevision. Втрачені відповіді на administrative-create не автоматично повторюються: клієнт перечитує список; гарантія ключа повтору стосується лише створення заявки.

## Переходи та побічні записи

API-06: assigned→in_progress — призначений спеціаліст; in_progress→waiting_requester — він же, text обов’язковий (public clarification); waiting_requester→in_progress — він же, наявна відповідь заявника після початку паузи або text обґрунтування; in_progress→resolved — він же, text обов’язковий (public solution); resolved→closed — власник із поточним solutionCommentId; resolved→in_progress — власник із тим самим solutionCommentId і text відхилення (public rejection). Звичайний коментар власника під час очікування самостійно стан не змінює. Призначення/перепризначення — API-04. Усі ці умови перевіряє сервіс; структурна OpenAPI-валідація їх не доводить. Успіх API-07 повертає нову версію Ticket, додане повідомлення читається API-08.

Уточнення користувача 05.11.2026: працівник може обробляти власну заявку за чинними дозволами підтримки, включно із самопризначенням координатора зі specialist-доступом. Видимість власної заявки завжди публічна: internal та відповідні події приховані незалежно від ролей; POST internal до власної заявки відхиляється. Звичайний public-коментар власника через API-07 має author_role=requester і не встановлює першу відповідь. Дозволені solution/clarification/resume_reason через API-06 мають author_role=specialist, навіть коли виконавець — власник; solution/clarification можуть встановити першу відповідь. Rejection — requester. Для чужого public-коментаря підтримки author_role=specialist за наявності specialist-дозволу, інакше coordinator. Контекст визначає сервер, не нове поле запиту. Деталі — security/access-matrix.md; приховані internal-поля не стають public.

## Помилки

| HTTP | code (приклади) | Поведінка клієнта |
|---|---|---|
| 400 | MALFORMED_REQUEST | Виправити JSON/параметр |
| 401 | UNAUTHENTICATED | Повторно ввійти; попередні дані не розкриваються |
| 403 | FORBIDDEN, CSRF_FAILED | Не повторювати дію без усунення причини |
| 404 | NOT_FOUND | Узагальнене повідомлення для відсутньої/недоступної заявки |
| 409 | VERSION_CONFLICT, STATE_CONFLICT, IDEMPOTENCY_CONFLICT, OPERATION_IN_PROGRESS, ACTIVE_ASSIGNMENTS, PRIORITY_LOCKED, SOLUTION_CHANGED | Перечитати доступний стан; не перезаписувати чужі зміни |
| 422 | VALIDATION_ERROR, INVALID_CATEGORY, INVALID_POLICY, INVALID_ASSIGNEE, INVALID_PREVIOUS_TICKET | Показати fieldErrors; зберегти коректно введені дані |
| 503 | STORAGE_UNAVAILABLE | Успіх не підтверджений; для створення — повтор з тим самим ключем |

Форма: code,message,correlationId,fieldErrors[]. message не містить SQL, stack trace, секретів або чужого змісту. Синтаксичний JSON/тип параметра — 400; коректний JSON з порушенням домену/довжини — 422. Невідома HTTP-операція поза контрактом — 405 з Allow. HTTP-статуси звірено з RFC 9110 [28]; конкретні code та сценарії — власні рішення.

## Пагінація та межі

limit=20 за замовчуванням, 1–100; курсор непрозорий, зв’язаний із фільтрами, поточним користувачем і порядком createdAt,id (для історії occurredAt,id). Змінювати фільтри між сторінками не можна без нового курсора. Курсор не надає доступу: дозволи перевіряються повторно. Адміністративні списки впорядковані id. Нові дані між сторінками можливі; незмінного міжзапитного знімка не обіцяно. Для одного Timing/Summary — один asOf і узгоджений знімок читання.

Немає API зміни категорії/черги наявної заявки, редагування/видалення коментарів та історії, фізичного видалення користувача/довідника, автоматичного перепризначення, зовнішньої пошти або брокера. Схеми Error та DTO не є переліком фізичних таблиць.

## Межа пароля — уточнення користувача 05.11.2026

LoginRequest.password і UserCreate.initialPassword мають maxLength=64 кодові точки Unicode. Для нового облікового запису доменний діапазон 15–64; вхід приймає непорожнє значення до 64 і перевіряє credentials. Значення понад межу відхиляється, не обрізається. Статична перевірка меж 64/65 та прикладів — `api/validation/password-length-2026-11-05.json`; це не запуск сервера.
